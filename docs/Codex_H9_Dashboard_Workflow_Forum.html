Реальный локальный проект

Как работать с Codex: от макета до проверенного Android APK

Публичная версия рабочего диалога о создании автономной приборной панели Haval H9: Codex проверяет окружение, меняет реальные файлы, генерирует графику, собирает APK, проводит аудит и отдаёт воспроизводимый комплект исходников.

Android 9 / API 28 Canvas 1920×720 36 секунд Автономные тестовые данные Без CAN и Binder Debug APK

Финальный контрольный кадр дизайна. Динамические значения и стрелки не запечены в статический фон APK.

i
Актуализация 11.08.2026: используйте готовую откалиброванную чёрную подложку и контрольный RGBA-слой системных иконок v2.4. Остальная компоновка нового скина свободна. Старые упоминания дополнительных масок ниже следует считать историей итераций, а не техническими требованиями.

Этап 1

Техническое задание задаёт границы

U Пользователь

Ты работаешь локально через Codex внутри выбранной рабочей папки. Изменяй реальные файлы проекта, запускай проверки и сохраняй результаты в workspace.

На основе утверждённого визуального макета создай автономный тестовый Android-проект приборной панели Haval H9. Используй Demo-проект как техническую основу, а существующий Classic — только как пример структуры. Внешний вид Classic нужно полностью заменить утверждённым макетом.

Ключевые требования исходного запроса
  • Android 9, minSdk=28, targetSdk=28, compileSdk=35.
  • Package net.adminrunet.h9clusterdemo, launcher .DashboardDemoActivity.
  • Нативный Android Canvas без WebView, логический холст 1920×720.
  • Прозрачное полноэкранное окно поверх штатного лаунчера.
  • DashboardState хранит снимок, DashboardDataSource отделяет источник от рендера.
  • DemoDashboardDataSource публикует только тестовые данные раз в 100 мс; цикл около 36 секунд.
  • Не добавлять CAN, GWM Adapter, Binder, реальные данные, автозапуск, Display ID 2, сеть и штатные системные значения.
  • Статический фон, отдельные стрелки и программно рисуемые динамические тексты.
  • Полностью прозрачное окно Яндекс карты и его растушёвка берутся из готовой откалиброванной чёрной подложки без изменения альфа-канала.
  • Контрольный RGBA-слой системных иконок v2.4 используется временно поверх макета: его нельзя масштабировать, включать в итоговый фон или применять как clipPath.
  • Для каждой динамической шкалы — своя таблица «значение → X → Y»: ноль, максимум, каждое подписанное деление и промежуточные значения.
  • Нельзя зеркалить или повторно использовать траекторию соседнего прибора без доказанной симметрии геометрии и одинакового распределения значений.
  • Диапазоны проверки: 0…220 км/ч, 0…8000 об/мин, 0…80 л, 40…130 °C, отрицательный/нулевой/положительный угол руля.
  • Подготовить layout_spec.md, четыре предпросмотра и машинно проверяемый отчёт.
  • До утверждения предпросмотра не собирать APK с новым дизайном.
C Codex — рабочий подход

Сначала была проверена фактическая рабочая папка, входные ZIP, README, Gradle, Manifest и весь Demo-код. Отдельно проверены JDK 17, Android SDK Platform 35, Build-Tools 35.x, Platform-Tools, Python, Pillow, NumPy и Gradle Wrapper.

Неизменённый baseline APK был собран до дизайнерских правок. После этого новый интерфейс был разложен на статический RGBA-фон, две отдельные стрелки и программные динамические значения. Контрольные изображения и валидация были сохранены локально, а сборка нового APK остановлена до одобрения.

Рабочая схема

Codex не «пишет ответ», а ведёт проект до результата

1

Инвентаризация

Пути, архивы, документация, исходники, Git-состояние и инструменты проверяются до изменений.

2

Baseline

Старый проект собирается первым, чтобы не спутать прежние ошибки с новыми.

3

Разделение слоёв

Статика, подвижные элементы и динамические тексты получают отдельные роли.

4

Математика

Каждая стрелка получает отдельную калибровку по своей финальной шкале; контрольные точки и безопасные прямоугольники задаются измерениями, а не «на глаз».

5

Машинная проверка

Размеры, alpha, маски, пересечения, диапазоны и удержание экстремумов проверяются скриптами.

6

Чистая поставка

APK, исходники, предпросмотры и отчёт получают размеры, SHA-256 и точные пути.

Этап 3

После одобрения — сборка, аудит и воспроизводимая поставка

U Пользователь

Предпросмотр автономной демки утверждён.

  1. Выполни предусмотренные проектом проверки.
  2. Собери debug APK.
  3. Если доступен эмулятор API 28 — проверь полный цикл; иначе честно укажи отсутствие.
  4. Проверь отсутствие GWM Adapter, CAN, Binder, автозапуска и реальных данных.
  5. Подготовь чистый ZIP без build, кэшей, ключей и паролей.
  6. Собери APK, ZIP, предпросмотры и отчёт в deliverables/final/.
  7. Укажи имя, размер и SHA-256 каждого файла.

Используй стандартную debug-подпись. Не используй production-ключ.

C Codex

Все графические проверки и 361 состояние цикла прошли. Android Lint сначала остановился на слишком большом date-based versionCode. Понижать его было нельзя: ранее установленный APK перестал бы обновляться. Поэтому Codex документированно отключил только HighAppVersionCode, сохранил номер версии и повторил Lint, unit-test task и сборку. 

lintDebug: PASS — 0 errors, 5 warnings
testDebugUnitTest: NO-SOURCE
assembleDebug: BUILD SUCCESSFUL
DEX checksums and identifier ordering: PASS

Скомпилированный Manifest и DEX были проверены отдельно. Итог: одна Activity, ноль permissions, services, receivers и providers; нет CAN, GWM, Binder, BOOT_COMPLETED, Android Car API, WebView, HTTP/HTTPS или Display ID 2. Activity создаёт только DemoDashboardDataSource.

Программа Android Emulator установлена, но AVD и образ API 28 отсутствуют, подключённых устройств нет. Поэтому Codex не заявил runtime-проверку, которой фактически не было. Программная проверка полного цикла по 361 состоянию прошла.

Практика

Почему такой способ работы надёжен

Сначала доказательства, потом изменения

Проверка окружения и baseline-сборка отделяют старые проблемы проекта от новых.

Условия должны быть измеримыми

Не «стрелка выглядит ровно», а совпадение с нулём, максимумом и каждым подписанным делением своей шкалы, проверка промежуточных значений и ноль пересечений.

Одобрение — реальная граница этапа

Codex остановил сборку нового APK до явного утверждения предпросмотров.

Нельзя заявлять непроверенное

Нет AVD API 28 — значит runtime-прогон честно отмечен как невыполненный.

Артефакт проверяется изнутри

Недостаточно удалить файл из source: состав собранного APK проверяется отдельно.

Поставка должна быть воспроизводимой

Чистый ZIP, отчёт, размеры и хеши позволяют другому человеку проверить результат.

Главный вывод Codex особенно полезен там, где запрос описывает не только желаемый результат, но и границы полномочий, порядок проверок, критерии приёмки и момент остановки. Тогда работа превращается из генерации фрагментов кода в управляемый инженерный процесс.
