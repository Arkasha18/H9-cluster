01 / Контекст

Не «сделай красиво», а управляемая инженерная работа

Владелец проекта заранее разделил источники истины, запретил самовольную смену дизайна, потребовал baseline до изменений и поставил обязательную паузу перед финальной сборкой. Это сделало результат проверяемым, а границы ответственности — однозначными.

1

Три источника истины

Demo отвечает за геометрию, production — за данные и Android-конфигурацию, маски — за защищённые зоны.

2

Сначала доказательства

Git-состояние, инструменты и неизменённая сборка проверяются до первой правки.

3

Две контрольные точки

Сначала перенос и предпросмотры; лишь после явного утверждения — release-компиляция и подпись.

СНАЧАЛА ПРОВЕРЬ ЛОКАЛЬНОЕ СОСТОЯНИЕ

До изменений:

1. найди все перечисленные пути и сообщи точные корни проектов;
2. полностью прочитай документацию, Gradle-файлы, Manifest и относящиеся к
   приборке исходники обоих проектов;
3. в каждом Git-репозитории выполни git status и git diff; не перезаписывай
   существующие пользовательские изменения;
4. проверь JDK 17, Android SDK и Gradle Wrapper;
5. собери неизменённый baseline основного проекта доступной безопасной
   конфигурацией без production-подписи;
6. сравни структуру Demo и production-проекта;
7. сообщи результаты baseline и только затем переходи к переносу.

Не подменяй готовый результат текстовыми советами. Все утверждения о сборке,
файлах и проверках подтверждай фактическими командами и существующими файлами.

1. Сопоставь каждый динамический элемент Demo с существующим полем

2. До реализации подготовь таблицу:
   элемент → поле Demo → поле ClusterState → data ID → формат → диапазон →

3. Не создавай вымышленные датчики и не подставляй тестовые значения.
4. Если для элемента нет подтверждённого реального источника, сообщи об этом и

5. Не меняй Binder-транзакции, идентификаторы данных и архитектуру источника
   без отдельной доказанной необходимости.
6. Перенеси алгоритмы сглаживания только там, где они уже проверены в Demo и
   не искажают фактическое значение.

КАЛИБРОВКА ДИНАМИЧЕСКИХ ШКАЛ

1. Для каждой шкалы перенеси отдельную таблицу `значение → X → Y`, измеренную
   по окончательному собранному изображению: ноль, максимум и каждое
   подписанное деление.
2. Не зеркаль и не переиспользуй траекторию другой шкалы без доказанной
   симметрии геометрии и одинакового распределения значений.
3. Между контрольными точками интерполируй движение по форме шкалы, сохраняя
   постоянный визуальный отступ указателя от неё.
4. Проверь каждую шкалу на всех контрольных точках и промежуточных значениях.
5. Добавь отдельные автоматические тесты контрольных точек, границ диапазона и
   промежуточных значений для каждой шкалы нового скина.
6. После изменения статической шкалы обязательно перекалибруй её динамический
   указатель.

08 / Разбор

Почему такой способ работы с Codex даёт результат

Описан конечный результат

Нужен не совет, а изменённый проект, предпросмотры, APK, ZIP и отчёт.

Названы источники истины

Codex не должен угадывать, какой проект главнее для дизайна, данных и масок.

Заданы запреты

Чёткий список «не переносить» защищает production от Demo-кода и тестовых значений.

Baseline обязателен

Состояние Git, JDK, SDK и исходная сборка превращают последующие выводы в доказательства.

Данные оформлены контрактом

Таблица до реализации исключает вымышленные датчики и проясняет fallback-поведение.

Проверки измеримы

Не «визуально вроде нормально», а точные пиксели alpha, маски, collision и хеши.

Есть точка остановки

Подпись и финальная упаковка начинаются только после явного одобрения preview.

Опасные действия исключены

Никакого ADB, установки на автомобиль, публикации PR или обращения с production-ключом без разрешения.
